## 1. First-run authority window — built, NOT applied

A user who logs a shift **before their first successful sync** is unflipped. With
the legacy read arm deleted they would see their first ever shift render as
nothing, permanently until connectivity, on the flow that already drew a
Guideline 4 rejection.

**#133 is CLOSED and must stay closed.** It put a trigger on `auth.users`, which
we can `CREATE` and **cannot `DROP`** — ownership is `supabase_auth_admin`,
postgres is not a member and cannot `SET ROLE` to it. A one-way door on live
signup. The rollback we signed off on could never have executed; the check that
"passed" did so because `DROP ... IF EXISTS` on a nonexistent object skips
*before* the permission check.

**Replacement, committed on `feat/stamp-authority-at-account-creation`:** a view
named `shift_migration_state` over a renamed ledger, returning the real row when
one exists and a synthesised authoritative row when none does and the account has
zero tip_entries. Entirely in `public/`, so ours to install and ours to drop, and
it reaches 1.0 users with no app update.

**Before it can be applied:**
- [ ] `account_creation_authority_test.sql` REWRITTEN, not edited — it still
      carries 18 references to the closed auth.users design
- [ ] `shift_fold_failures` asserted empty in **every** fold test
- [ ] the cost paragraph, with the JSON-harness numbers

**Already established, do not re-derive:**
- `security_invoker = on` is mandatory; without it the view runs as owner and
  leaks across accounts. Demonstrated in both directions.
- Expose exactly the client's **five** columns, not all — a server reader wanting
  counters then fails loudly instead of silently receiving synthesised NULLs.
- **No `INSTEAD OF` triggers.** A writable view would have hidden the fold defect
  entirely.
- Every server-side **reader** repoints to the base table, not just writers. The
  one-shot's own `unmigratedCount > 0 or not authoritative` would otherwise read a
  synthesised row and conclude an account migrated when nothing migrated it.
- Cost: the derived branch is ~696–783 buffers vs 1 on the fast path, but it is
  **bounded** — the fold converts and the one-shot stamps, so an account is on the
  fast path from its first logged shift. Optional tuning: a `not exists` pre-check
  on `unmigrated_legacy_rows` (870 buffers to answer "nothing outstanding").
